# 決策紀錄

## D1：目標使用者與規模

- 第一階段：小團隊內部自用，約 15 人。
- 不做：多租戶、對外訂閱、計費。
- 核心痛點：誰要做什麼、何時到期、現在進度如何。

## D2：資料層級

- 單一團隊（無工作區概念）→ 專案 → 任務。
- 任務可無限展開子任務，且**一個任務可有多個 parent**。
- 因此任務之間是關聯鏈路（圖，DAG），不是單純的樹。
- 待釐清：關聯的語意、循環處理、進度如何彙總。

## D3：任務關聯語意

- 第一版只做「包含」關係（多 parent 的 DAG）。
- 禁止循環：建立關聯時必須檢查，A 不能直接或間接成為自己的子孫。
- 「依賴／被擋住」之後以獨立的關聯類型加入，不在第一版。

## D4：進度彙總

- 第一版手動：每個任務自己標記完成，不自動連動 parent。
- parent 僅顯示「子任務 n/m 完成」作為參考。
- 自動彙總（DAG 連鎖更新）之後再評估。

## D5：任務與專案

- 一個任務可屬於多個專案（multi-homing，Asana 概念）。
- 任務與專案為多對多關係。
- 待釐清：子任務的專案歸屬是否繼承 parent、任務可以不屬於任何專案嗎。

## D6：專案歸屬不繼承

- 每個任務自己決定屬於哪些專案，不繼承 parent。
- 專案頁面只列出明確掛在該專案的任務。
- 子任務在 parent 底下展開時照常顯示，不論它掛在哪個專案。

## D7：任務可不掛專案；每人有綁死的個人根

- 任務可以不屬於任何專案。
- 每個使用者名下有一個固定、不可刪除的個人根（root），自己建立的任務都掛在這裡。
- 待釐清：個人根的資料形態（是一個 task 節點，還是特殊容器）。

## D8：個人根是特殊 task 節點

- 使用者註冊時自動建立一個個人根 task 節點，不可刪除、綁定該使用者。
- 使用者建立的任務預設是個人根的子任務，沿用同一套 parent 關聯。
- 所有任務都能往上追溯到某個人的根，不存在沒有 parent 的孤兒任務。
- 待釐清：任務掛到別人的任務下時的權限；個人根是否可被他人看見。

## D9：可見性預設私人

- 個人根底下的任務預設只有本人看得到。
- 被掛進專案，或指派給別人時，對相關人可見。
- 影響：所有任務查詢都要做可見性判斷。
- 待釐清：「相關人」的精確定義（專案成員？指派人？被掛的 parent 的擁有者？）。

## D10：專案成員制

- 專案有成員名單；成員看得到專案內所有任務，非成員看不到。
- 需要專案成員表（project_member）。
- 待釐清：任務同時掛在多個專案時，可見性取聯集（任一專案的成員即可見）還是其他；成員角色（是否分管理者／一般成員）；誰能建立專案、加成員。

## D11：多專案可見性取聯集

- 任務掛在多個專案時，任一專案的成員都看得到。
- 掛進專案等同分享給該專案所有成員。
- 任務可見者 = 本人 ∪ 所掛專案成員（指派人等其他規則待釐清）。

## D12：指派即分享

- 被指派人看得到該任務，即使任務沒掛專案。
- 任務可見者 = 建立者（個人根擁有者）∪ 指派人 ∪ 所掛專案成員。
- 待釐清：一個任務可指派幾人（單人 vs 多人）；子任務可見性是否獨立於 parent。

## D13：單一負責人

- 一個任務最多一個 assignee（可為空）。
- 多人協作以拆子任務表達。

## D14：可見性隨 parent 向下傳遞

- 能看到某任務，就能看到它所有子孫任務（沿包含關係向下）。
- 多 parent 下：任一祖先可見，即可見（對 DAG 取祖先閉包）。
- 影響：把任務掛到可見範圍較大的 parent 下，會讓該任務及其子孫被分享出去（洩漏風險，需在 UI 提示）。
- 影響：可見性查詢需遞迴（recursive CTE 或 closure table）。
- 待釐清：誰有權限建立／移除 parent-child 關聯。

## D15：建立／移除關聯的權限

- 建立 parent→child 關聯：需同時看得到 parent，且對 child 有操作權（例如自己的任務）。
- 掛上去前 UI 提示「此任務將對 <範圍> 可見」，確認後生效。
- 移除關聯：看得到的人都能移除；只移除關聯，不刪任務本身。
- 建立關聯前必須通過循環檢查（D3）。

## D16：固定狀態欄位

- 所有專案共用固定狀態，不做專案自訂。
- 四態：待辦（todo）、進行中（in_progress）、擱置（pending）、完成（done）。
- 完成是唯一終態。

## D17：擱置（pending）可指定被哪些任務擋住

- 任務設為擱置時，可指定「被哪些任務 pending」（blocked by）。
- 這等於把 D3 延後的「依賴」關係拉進第一版，與「包含」是不同類型的關聯。
- 依賴關係同樣需要循環檢查（A 不能直接或間接被自己擋住）。
- 待釐清：擋住的任務全部完成後，狀態是否自動恢復。

## D18：擱置規則

- blocker 清單為選填。
- 不變量：blocker 清單非空 ⇒ 狀態必為 pending。要離開 pending，必須先清空 blocker。
- 反向不成立：pending 可以沒有 blocker（例如等外部因素）。
- blocker 全部完成後不自動恢復，只提示，由負責人手動處理（延續 D4 手動原則）。

## D19：已完成的 blocker 自動移除

- blocker 完成時，自動從被擋任務的 blocker 清單移除。
- 清單清空後狀態維持 pending，不自動恢復；由負責人手動改狀態（與 D18 一致，狀態只由人改）。
- 已移除的 blocker 若之後被重開，不會自動加回。
- 不保留「曾被誰擋住」的紀錄（若要追溯需靠活動紀錄，第一版不做）。

## D20：第一版視圖

- 只做清單視圖：「我的任務」與「專案任務清單」，清單內可展開子任務。
- 看板、時間軸、日曆等之後再加。

## D21：多 parent 的清單顯示

- 每個 parent 底下都完整顯示該子任務；它們是同一筆資料，編輯同步。
- 子任務旁標示「另有 N 個 parent」。
- 展開一定會結束，因為循環已被禁止（D3）。
- 待釐清：DAG 展開時子孫重複出現的效能上限（深度或數量）。

## D22：任務欄位

- `title`、`assignee`（D13）、`status`（D16）。
- `description`：Markdown，需要可編輯並渲染 Markdown 的編輯器。
- `start_date`：開始日，選填。
- `due_date`：到期日，必填。
- 只有到期日、沒有開始日時，以里程碑方式顯示（為後續甘特圖預留）。
- 每個任務下有討論串（留言）。
- 待釐清：`priority` 去留（現有 schema 已有）；討論串的範圍與形態。

## D23：先移除 priority

- 第一版不做優先級；現有 schema 的 `priority` 欄位移除。
- 日後需要再加。

## D24：討論串為扁平留言

- 每個任務一條依時間排列的留言流，內容支援 Markdown。
- 留言歸屬於任務本身；多 parent 下，從任何 parent 展開看到同一條討論串。
- 可見性與任務相同（D14）。
- 針對議題的深入討論以子任務表達，不做巢狀回覆。

## D25：留言可編輯與刪除

- 留言作者本人可編輯、刪除；刪除為真刪除。
- 編輯後顯示「已編輯」標記，不保留編輯歷史。

## D26：邀請制與角色

- 邀請制，不開放自行註冊。
- 系統啟動時必須先設定「系統管理員」。
- 之後加入的成員有兩種權限：管理人（可邀請其他人）、一般用戶（不可邀請新人）。
- 待釐清：系統管理員與管理人的差別；初始系統管理員如何建立；邀請流程（email 或連結）；停用／移除成員。

## D27：系統管理員的權限

- 系統管理員：邀請成員、改角色（升降管理人）、停用／移除帳號。
- 管理人：只能邀請成員。
- 一般用戶：不可邀請。
- 不變量：系統至少保留一位系統管理員，不能把最後一位降級或停用。
- 待釐清：初始系統管理員如何建立；邀請流程；被停用成員的任務與留言如何處理。

## D28：初始系統管理員用環境變數建立

- `.env` 設定 `ADMIN_EMAIL`、`ADMIN_PASSWORD`。
- 啟動時若系統內沒有任何使用者，自動建立系統管理員，並同時建立其個人根（D8）。
- 不做 `/setup` 設定頁（避免部署後、設定前被搶先註冊）。
- 已有使用者後，這兩個變數不再生效。

## D29：邀請連結

- 管理人（或系統管理員）輸入對方 email，系統產生一次性邀請連結，由邀請人自行轉交，不寄信。
- 連結有效期限（預設 7 天）、只能使用一次；對方用它設定密碼完成註冊。

## D30：部署於 Cloudflare

- 目標平台 Cloudflare（Workers / Pages），資料庫用 D1（SQLite）。現有 `drizzle.config.ts`、`getDb(d1)` 已是 D1。
- 影響：D28「啟動時 seed」在 Workers 沒有常駐啟動流程，需改寫實作方式（待釐清）。
- 影響：D14 的遞迴可見性查詢用 SQLite recursive CTE，D1 支援。
- 影響：需注意 Workers 的 CPU 時間與 D1 的查詢限制，DAG 展開要有上限。
- 待辦：確認 adapter 改為 `@sveltejs/adapter-cloudflare`，並建立 `wrangler` 設定。

## D31：初始管理員用手動 seed 腳本（取代 D28 的啟動時建立）

- 部署後由部署者執行一次 seed 指令（例如 `pnpm seed`），透過 D1 HTTP API 建立系統管理員與其個人根（D8）。
- `ADMIN_EMAIL`、`ADMIN_PASSWORD` 只在執行腳本的本機使用，不放進線上環境。
- 系統內已有使用者時，腳本拒絕執行。
- 步驟記錄在 README。

## D32：停用而非刪除成員

- 成員只能被停用：無法登入，但帳號、個人根、任務、留言全部保留，顯示為「已停用」。
- 停用者負責的任務維持原指派人，等其他人改派。
- 不提供真刪除；日後若要清除資料再做匿名化。
- 停用者從專案成員名單的可見性判斷中排除（待實作時確認）。

## D33：第一版不做通知

- 被指派的任務出現在「我的任務」，使用者自行查看。
- 不做站內通知、不寄信。看實際使用是否漏看再評估。

## D34：個人根豁免到期日

- 個人根只是「我的任務」的容器，不是真正的任務：無到期日、不顯示在清單、不上甘特圖。
- 其餘所有任務（含個人根底下的個人任務）`due_date` 必填。
- 資料庫層以 CHECK 保證：`root_owner_id IS NOT NULL OR due_date IS NOT NULL`。

## D35：UI 套件採用 shadcn-svelte

- 使用 shadcn-svelte（bits-ui + Tailwind 4），元件原始碼放在 `src/lib/components/ui/`，不自己手刻基礎元件。
- 路徑別名沿用專案的 `#lib`（`components.json` 已設定）。
- 需要新元件時用 `pnpm dlx shadcn-svelte@latest add <name>`。
- 已安裝：button、input、label、card、alert、badge、native-select。

## D36：seed 改用 wrangler d1 execute，個人根延後建立（修訂 D31）

- seed 腳本（`pnpm seed`）以 `wrangler d1 execute DB --local|--remote` 寫入，不走 D1 HTTP API；預設 `--local`，`--remote` 必須明確指定。
- wrangler 不保證多個陳述式為同一交易。wrangler 執行失敗，或回報成功但只有 user 沒有 credential account 時，腳本會嘗試刪除這個新建的半成品 user 後失敗，可重跑。若清除本身也失敗（或程序中途被終止），會留下沒有密碼的 user、之後 seed 因已有使用者而拒絕，需手動 `DELETE FROM user`；腳本會印出此提示。
- seed 目前不建立系統管理員的個人根（D8），因為 task 表要到實作順序第 3 步才存在。第 3 步必須為既有使用者（含 seed 的管理員與已接受邀請的成員）回補個人根，並讓之後的邀請接受流程自動建立。

## D37：邀請連結隨邀請人失效

- 接受邀請時檢查邀請人：必須仍是管理人以上（manager 或 system_admin）且未被停用，否則拒絕。
- 邀請人被降級或停用後，其尚未使用的連結即失效。

## D38：成員 email 對所有登入者可見

- `/members` 列出名字、email、角色、狀態，所有登入成員皆可看。
- 理由：內部小團隊，email 即登入帳號，指派時需要分辨同名的人。

## D39：邀請可列出與撤銷

- 成員頁新增「待使用的邀請」區塊：email、邀請人、到期日；連結本身不再顯示（只存雜湊）。
- 撤銷 = 作廢該邀請，連結立即失效。
- 權限（暫定，待使用者確認）：管理人以上可看列表；邀請人本人或系統管理員可撤銷。

## D40：同 email 只保留一張有效邀請

- 對同一 email 發新邀請時，自動作廢該 email 先前尚未使用的邀請。
- 同一 email 同時只會有一張有效邀請；重發（對方弄丟連結）即取代舊的。

## D41：個人根懶建立

- 使用者第一次進「我的任務」時，若沒有個人根就自動建立；seed、邀請接受不建根。
- 以 `root_owner_id` 唯一索引保證每人只有一個根，併發建立時以唯一約束擋下並重讀。
- 修訂 D36 的「補建」說明：不需要一次性回填。

## D42：「我的任務」清單

- 合併兩種來源：個人根的直接子任務（自己建）＋指派給我的任務（被指派），每筆標示來源。
- 預設只顯示未完成，依到期日排序；已完成收在可展開的區塊。
- 必須可篩選（filter）。
- 第 3 步只顯示個人根的直接子任務；更深的子孫待第 4 步（DAG）。
- 待釐清：可篩選的維度（狀態、來源、到期區間、關鍵字？）、篩選條件是否記在 URL。

## D43：「我的任務」篩選維度

- 狀態（四態多選）、來源（自己建／被指派）、到期（已逾期／本週／全部）、所屬專案。
- 不做關鍵字搜尋、自訂日期區間。
- 篩選條件放在網址 query string，重新整理與分享連結不丟條件。
- 「所屬專案」篩選要等第 5 步建立 project 表後才能實作；第 3 步先做其餘三項，並讓篩選機制可擴充。

## D44：任務建立與編輯

- 「我的任務」頂端有快速新增列：標題＋到期日（必填），其餘進詳情頁。
- 詳情頁為獨立路由 `/tasks/[id]`：編輯 title、description（Markdown）、assignee、status、start_date、due_date。
- Markdown 編輯器採「文字框＋預覽切換」，不引入重量級編輯器套件；渲染需消毒（防 XSS）。
- 詳情頁同時是之後子任務（第 4 步）與留言串（第 7 步）的落腳處。

## D45：任務編輯權限（第 3 步範圍）

- 建立者與指派人都能編輯全部內容欄位（title、description、status、start_date、due_date）。
- 只有建立者能改指派人與刪除任務。
- 專案成員的編輯權限待第 5 步另行決定。

## D46：任務真刪除

- 刪除為真刪除（從資料庫移除），UI 需確認提示。
- 第 3 步任務尚無子任務與留言；刪除有子孫或留言的任務如何處理，待第 4、7 步再議。

## D47：子任務的兩種新增入口

- 詳情頁「新增子任務」：輸入標題與到期日，直接建立新任務並掛在目前任務底下。
- 詳情頁「掛上既有任務」：從自己看得到的任務中選取，掛到目前任務底下（多 parent 的來源）。
- 掛上既有任務前顯示分享範圍提示（D15）；建立關聯前必須通過循環檢查（D3）。

## D48：每個任務至少有一個 parent，個人根是預設

- 不變量：每個非根任務至少有一個 parent。沒有其他 parent 時，parent 就是個人根。
- 新建子任務只掛在指定的 parent 下，不同時掛個人根。
- 把有個人根 parent 的任務掛到別的任務下時，個人根的關聯被取代；其他 parent 都被移除時，退回個人根。
- 「我的任務」只列頂層任務（parent 是個人根）加上指派給我的任務（D42）。
- 待釐清：退回的是誰的個人根（建立者或操作者）。

## D49：頂層歸屬由「沒有 parent」推導（取代 D48，修訂 D8、D42）

- `task_parent` 只存真正的 parent，不再存「個人根 → 任務」的關聯；既有的根關聯以 migration 移除。
- 頂層任務＝沒有 parent 的任務。歸屬者＝指派人，沒有指派人則是建立者。
- 移除最後一個 parent 時自動退回此推導，不需要特別邏輯。
- 「我的任務」＝歸屬者是我的頂層任務，加上指派給我的任務（含有 parent 的）。
- 新增第二份清單「我指派給別人的」：我建立、指派人不是我的任務，否則指派出去後建立者就看不到。
- 個人根仍是每人一個、不可刪除的容器節點（D41），但不再出現在 `task_parent` 中。
- 影響：D14 可見性向下傳遞的根改為「歸屬者」；第 3 步的可見性（建立者或指派人）維持。

## D50：掛 parent 的權限

- 建立 parent→child 關聯：必須看得到 parent，且是 child 的建立者或指派人（D45 的操作權）。
- 移除關聯：同樣需要對 child 的操作權（比 D15「看得到的人都能移除」更嚴，修訂 D15）。
- 理由：只有有操作權的人能動任務結構，避免別人的任務被意外掛到不相干的地方。

## D51：看不到的 parent 只顯示數量

- 任務詳情顯示 parent 時：看得到的 parent 顯示名稱並可連結；看不到的合併成「另有 N 個你看不到的 parent」，不洩漏其內容。
- 理由：讓使用者知道改動可能影響別處，同時不洩漏無權限的資料。

## D52：子任務逐層載入

- 清單與詳情只預設展開一層，點開才載入下一層；深度不限、不設硬上限。
- 每個任務旁顯示「子任務 n/m 完成」（D4），讓使用者決定要不要展開。
- 理由：DAG 下整棵子樹一次載入可能因共用子樹而指數放大，逐層載入沒有爆量風險。

## D53：刪除有子任務的任務時，詢問使用者（修訂前一版）

- 刪除一個有子任務的任務時，跳出提示讓使用者二選一：
  1. 連同關聯的整棵子樹一起刪除。
  2. 只刪這個任務，子任務保留並掛回 root。
- 「掛回 root」：子任務失去最後一個 parent 後，先掛到被刪任務所屬的專案（第 5 步後生效）；沒有專案則依 D49，歸屬者為指派人，無指派人則為建立者。
- 提示需寫明受影響的數量（會被刪的任務數／會失去 parent 的任務數）。
- 沒有子任務時，沿用單純的刪除確認（D46）。
- 待釐清：整棵子樹刪除時，被其他 parent 共用的子孫怎麼處理；子樹中不是自己建立的任務是否能刪。

## D54：整棵子樹刪除不刪共用的子孫

- 只刪「所有 parent 都在被刪範圍內」的子孫；仍有範圍外 parent 的子孫保留，只失去被刪範圍內的 parent。
- 提示寫明「共用的 N 個子任務會保留」。
- 保留的子孫若因此沒有 parent，依 D53 的「掛回 root」規則處理。

## D55：整棵子樹刪除只刪自己建立的任務

- 樹刪除只刪「我建立」且符合 D54 的子孫；不是我建立的子孫一律保留，並依 D53 掛回 root。
- 提示寫明「N 個不是你建立的任務會保留」。
- 理由：刪除權限（D45）不因任務掛在我名下而擴大，避免把別人的任務掛過來再刪掉來繞過權限。

## D56：只有 manager／system_admin 能建專案

- 建立者自動成為該專案的 owner。一般成員（`member`）不能建專案。

## D57：專案成員分 owner／member

- `project_member` 帶角色：`owner`（管理者）、`member`（一般成員）。

## D58：成員管理只有 owner（或 system_admin）

- 只有該專案 owner 或 `system_admin` 能加／移除成員、改成員角色、改專案資料、封存。
- 只能加入已啟用（未被停用）的帳號。

## D59：掛任務進專案的權限

- 任務的建立者或指派人，且是該專案成員，才能把任務掛進專案或取消掛接。
- 理由：掛接會讓全體專案成員看到該任務及子孫（D14），須有編輯權（D45）才能決定；且須是專案成員，避免塞進自己沒參與的專案。

## D60：專案只能封存，不刪除

- 封存＝唯讀、預設清單隱藏、任務不動；owner 或 `system_admin` 可封存／取消封存。
- 第一版不提供專案刪除。

## D61：專案欄位

- `name`（必填、不要求唯一）、`description`（選填，Markdown，沿用 D44 的消毒渲染）。日期與狀態有需求再補。

## D62：最後一個 owner 不能離開或降級

- 專案永遠至少一個 owner；要換人須先指定另一位 owner。DB 交易內檢查。
- 帳號被停用不自動移出專案；owner 都被停用時，`system_admin` 可補人。

## D63：只有成員看得到專案

- 專案名稱與成員名單只對專案成員可見；`system_admin` 可見全部。

## D64：封存不影響可見性

- 封存專案的成員資格仍提供任務可見性（D14 不變）。
- 封存後禁止：掛入新任務、取消掛接、改成員、改專案資料（封存＝專案唯讀，任務集合不變）。任務本身的編輯權不變。

## D65：blocker 延後，第一版不做（D17–D19 延後）

- 第一版不做 blocker（依賴關係）；「擱置」只是一般狀態（例如等外部因素），沒有 blocker 清單。
- D17–D19 延後到確實出現兄弟任務或跨專案互等的需求時再做；屆時已討論的方向：只有被擋任務的建立者或指派人能增減 blocker、只能選自己看得到的任務；被擋與 blocker 雙向顯示摘要（標題、狀態、到期日、指派人），無權限者點不進詳情；新增 blocker 自動設為擱置；已完成的任務不能加 blocker 也不能被選為 blocker。
- 理由：工作主要以父子關係組織；blocker 是另一套關聯（循環檢查、摘要可見性、自動移除），成本高，之後補不影響既有資料。

## D66：子任務全部完成，父任務才能完成（修訂 D4）

- 把任務改為完成時，檢查其直屬子任務；有未完成者就拒絕，提示「還有 N 個子任務未完成」（N 含自己看不到的，只給數量）。
- 只在標記完成那一刻檢查；之後子任務重開、或在已完成的任務下新增／掛上子任務，都不連動父任務（延續 D4「狀態只由人改」）。
